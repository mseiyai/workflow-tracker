# Working instructions for Workflow Tracker

## Context
- Read README.md, docs/product.md, and the requested issue before editing.
- Treat repository files as the current project record.
- Do not assume a previous lesson or issue has been completed.

## Workflow
- Check the current directory, branch, and Git status first.
- Preserve existing changes. Do not reset, clean, or overwrite unrelated work.
- Implement only the requested issue.
- Keep changes small and explain assumptions.
- Do not add dependencies or frameworks unless the issue requires them.
- Do not commit, push, or deploy unless explicitly requested.

## Python
- Use the standard library for the current milestone.
- Keep counting logic separate from file reading and printing.
- Resolve project data paths from the script location.
- Do not modify data/tasks.json merely to make checks pass.

## Verification
Run from the repository root:
- python3 backend/summary.py
- (cd backend && python3 summary.py)
- python3 -m unittest discover -s tests -v, once tests exist
- git diff --check

Report actual commands, results, and any checks not run.
Zero discovered tests does not count as successful verification.

## Issue-driven development
- Work on one explicitly named issue at a time.
- Confirm the current branch and Git status before editing.
- For behavior changes, first add or update a focused test.
- Observe the expected test failure before implementing the behavior.
- Implement the smallest change that satisfies the issue.
- Run the focused tests, then the complete test suite.
- Review the complete diff against the acceptance criteria.
- Do not mark an issue verified without recording observed evidence.
- Do not commit, push, merge, or deploy unless explicitly requested.

## Python dependencies

- Python code must support Python 3.13 or newer.
- Use the repository `.venv` for Python commands.
- Record runtime and test dependencies in `requirements.txt`.
- Add dependencies only when approved by the current issue.
- FastAPI and HTTPX are approved for Issue 004.

## API verification

- Run focused API tests before the complete test suite.
- API endpoints must reuse business logic from existing modules.
- Read-only API work must not modify `data/tasks.json`.

## Frontend

- React and TypeScript source belongs under frontend/src/.
- Avoid `any`; define types for API request and response data.
- Keep HTTP requests outside presentation components.
- Every remote-data view must account for loading, error, empty, and success states.
- Do not hard-code task records or summary counts.
- Run `npm run build` after frontend changes.
- Do not add frontend dependencies unless the current issue requires them.

## Database migrations

- Represent schema changes with SQLAlchemy models and Alembic migrations.
- Inspect every autogenerated migration before applying it.
- Read the database connection from `DATABASE_URL`; never commit credentials.
- Do not call `Base.metadata.create_all()` during application startup.
- Do not run destructive migrations without explicit approval and a backup plan.
- Seed commands must be safe to run more than once.

## Database-backed API

- Keep SQLAlchemy queries in repository classes, not route functions.
- Use one SQLAlchemy Session per HTTP request.
- Application code must not connect to the test database by default.
- Integration tests must refuse to clean a database whose name does not end in `_test`.
- Apply Alembic migrations instead of creating tables directly in tests.
- Preserve API contracts when replacing a storage implementation.

## Containers

- Keep container configuration reproducible and free of committed secrets.
- Run application processes as a non-root user.
- Use Compose health checks for readiness-dependent services.
- Apply Alembic migrations before starting the API.
- Use service names, not localhost, for communication between containers.
- Preserve PostgreSQL with a named volume.
- Never run `docker compose down -v` without explicit approval because it
  deletes the project’s named volumes and database contents.
- Run docker compose config, image build, health, migration, and persistence
  checks after container changes.


## Continuous integration

- Pull requests must pass backend tests, database migration checks, and the
  frontend production build.
- CI databases must be temporary test databases. Never connect CI to staging
  or production databases.
- Keep GitHub Actions permissions read-only unless an issue explicitly
  requires additional permissions.
- Use `npm ci`, not `npm install`, in CI.
- Keep deterministic checks in CI even when Codex also performs a review.

## Code review rules

Treat these as blocking findings:

- Production credentials or database URLs in code or workflow files
- Deployment or image publishing triggered by an untrusted pull request
- Model changes without an Alembic migration
- Tests that silently skip when PostgreSQL is unavailable
- Broad GitHub Actions write permissions without a documented need

## Configuration invariants

- Never commit credentials or populated `.env` files.
- Backend startup, migrations, and tests require an explicit database URL;
  do not add a hidden SQLite or production-database fallback.
- CI integration tests must use an isolated database whose name ends in
  `_test`.
- The supported project baseline is Python 3.13.
- Dependency manifests contain intentional application dependencies.
  Validate them from a clean environment rather than copying an unrelated
  global environment.
